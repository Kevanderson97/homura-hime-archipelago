# Homura-Hime AP world

Python world for Archipelago 0.6.x (`homura_hime/`, version in `homura_hime/archipelago.json`). Player-facing docs:
`homura_hime/docs/en_Homura-Hime.md` (game page) and `setup_en.md`. The sections below describe how the world works.

## Files

| File | Contents |
|------|----------|
| `__init__.py` | The world: item pool, regions, rules, counters, slot data, Universal Tracker support |
| `shop_budget.py` | The post-fill check that what the seed makes everybody buy in the shops is affordable in time |
| `options.py` | Options and option groups |
| `game_data.py` | Loads the data contract and derives the lookup tables |
| `data/*.json` | The data contract shared with the plugin, generated by `../tools/build_data.py` |
| `test/` | World tests (generation per option set, rules, pool, shop budget) |

The data contract (`../data/locations.json`, `items.json`, `regions.json`) is generated by `tools/build_data.py`, which
also copies it into `homura_hime/data/`. Ids are frozen in `../data/id_registry.json`; an item keeps its id when its
name changes. Shop prices (`price`), vanilla Konpeito payouts (`konpeito`), Harumi thresholds (`petals`) and the
Konpeito filler sizes (`ladder`) live in the contract, not in Python.
Locations carry a `category` (chest, shop, harumi, encounter, ...) and items a `type` (combo, skill, omamori, currency, ...),
the word Hollow Knight and several other worlds use for their items; the plugin's `LocationRecord.Category` and
`ItemRecord.Type` read the same fields.

## Develop and test

```
# one-time: an Archipelago 0.6.x source checkout with its virtual environment, and a link to this world:
#   New-Item -ItemType Junction -Path <Archipelago>\worlds\homura_hime -Target <repo>\apworld\homura_hime   (Windows)
#   ln -s <repo>/apworld/homura_hime <Archipelago>/worlds/homura_hime                                         (Linux/macOS)
python tools/build_data.py                                  # only after the data in data/ changed
cd <Archipelago>
python -m pytest worlds/homura_hime/test -q     # this world's tests
python -m pytest test/general -q                # Archipelago's conformance suite, all worlds
```

Code follows AP's `docs/style.md` (120 characters per line, double quotes, f-strings).

`sample/Homura-Hime.yaml` is a player yaml with every option, written by Archipelago's own template generator
(`python tools/make_sample_yaml.py`); `test/test_sample_yaml.py` fails when an option or the world version changes and the
sample was not regenerated. Copy it into `Players/` and edit the values to generate a seed.

## Content

- 332 locations: chests, Senbei, journals, 42 shop slots, stage clears, Harumi, hand-overs, trials, the tutorial reward,
  110 encounter clears (`encounter_clears`, default on) and 4 ambush rewards (`encounter_rewards`).
- 97 item definitions. Pool: the fixed progression/useful items, Special Hanami Dango, Senbei (single and "2 Senbei"),
  one Konpeito item per vanilla Konpeito payout, Full Heal / Ultimate Charge and the currency filler (Konpeito and Sakura).
- Regions: Menu, Hub, one region per sub-chapter (chained inside a chapter) and the finale. Events: `Chapter N Entered`,
  `Chapter N Cleared`, `Victory`.

## Logic

- **Chapters**: entered in play order (vanilla or randomized); with `level_unlock_items` they need their unlock item (and,
  in vanilla order, the previous chapter cleared). The finale needs all eight cleared.
- **Level 1** runs Area 1 -> Demonic Realm -> Areas 2 and 3 -> boss: the flower leaves Area 1, the dash skill crosses the gap at the start of Area 2 (so the Demonic Realm and its chests need no dash skill).
- **Key items**: `SCENE_REQ` / `TRANSITION_REQ` gate parts of chapters; Level 1 also needs a dash skill (started with, or
  placed early). With `advanced_movement_required` no dash skill is required (the gap is crossed by parrying the laser), none
  is placed early, the dash skills are plain useful items and shops may sell them. Gate items are kept out of the unmapped part of their own area (`GATE_PLACEMENT_LIMIT`).
- **Shops**: a slot needs its tier of cleared chapters (at least one), `1.5 x` the Konpeito paid out must cover its
  price, and the Senbei received must cover its Senbei price (17 slots cost 1-3 Senbei, 26 in all). Senbei cannot be
  farmed, so they are counted exactly, with no factor. Dash skills of the world never go into its shop, and neither does
  its own Konpeito (the shop is paid with it, so that would be a wasted purchase); Senbei may be sold there.
- **Shop budget** (`shop_budget.py`, in `stage_finalize_multiworld`, after progression balancing): the seed is played
  sphere by sphere by a player who buys only the progression in shop slots; for each such item the first sphere that
  needs it is found (by taking it out and replaying from its sphere), and the items needed by a sphere must cost no more
  than the money and the Senbei before it. Otherwise the dearest (in the resource that is short) is swapped with a filler/useful item outside the shops that is
  reachable no later than the slot. An unrepairable seed is kept with a warning: Konpeito is unlimited in the game.
  Built for large multiworlds: replays only check each original sphere's locations once and stop at the last sphere
  where the budget could fail, the state is only copied before spheres that hold a purchase, and a repair resumes the
  playthrough from before the moved item instead of starting again.
- **Harumi**: one cleared chapter at least (HARUMI_MIN_CLEARED), then 280 Sakura per cleared chapter plus the Sakura items held. The highest threshold (2,300) is above what
  eight chapters give (2,240), so the pool always holds at least 60 Sakura in items.
- **Counted items**: the large Konpeito (3,000 and up) and Sakura (30 and up) items and the "2 Senbei" pieces (the single
  Senbei when the pool has no pairs) are `progression_skip_balancing` so
  the logic sees them (only advancement items enter the state), with running totals kept in `collect`/`remove` (as The
  Messenger does with shards; Hollow Knight's grubs are the same idea, counted with `state.count`). What they add up to
  is scaled by all of that currency in the pool over the counted part (`money_scale`, `petal_scale`, `senbei_scale`), so holding every
  counted piece means holding the whole pool. The small pieces are plain filler: each counted item is one more
  advancement item for the fill, and fill time grows with them (50 Homura-Hime players: 17 s counting every piece,
  4 s now). All currency items have `flags` 0, so clients see filler. Cleared chapters are counted the same way.- **Stage clears** need the chapter cleared; the festival stall needs the Inugami Certificate; Desire Circle's hand-over
  waits for the first cleared chapter.
- `optional_location_importance` below 100 excludes that share of optional locations from progression/useful items.

## Slot data

`world_version`, `level_order`, `level_order_mode`, `start_dash_skill`, `dango_count` and the toggles in
`SLOT_DATA_TOGGLES`. The plugin accepts worlds of its own major.minor version (`plugin/Archipelago/SlotData.cs`).
`interpret_slot_data` lets Universal Tracker regenerate the world from it.

## Known simplifications

- Scene-to-sub-chapter assignment (`tools/build_data.py`, `CHAPTERS`) follows the game's portal order; a few scenes are
  placed by judgement (Level 3 Secret Zone, Level 5 Ikai, Final P0). Check against a playthrough.
- Level 3 Area 5, Level 4 Area 3 and Level 5 Area 5: the part of the area behind the Nurikabe is not mapped, so the gate
  item may not be placed in those scenes (except at its own hand-over).
- Journal location names are derived from the code names until the game's own note names are added to
  `data/localized_names.tsv`.

## Names

- **Items** carry the name the game shows (`data/localized_names.tsv`, read from the game's localization).
- **Locations** have a readable name (`Level 2 Area 5: Chest 1`, `Shop: Blazing Thrust`) generated by
  `tools/location_names.py`, and a stable internal `key` (`chest/Level_2_Area_5_Main/1`) used by the plugin and the id
  registry. In code use `NAME_OF_KEY` / `KEY_OF_NAME`.
